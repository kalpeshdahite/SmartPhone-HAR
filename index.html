Can a phone's motion sensors tell what you are doing?

Smartphone-HAR recognises activities such as walking, sitting and climbing stairs from raw accelerometer and gyroscope signals, tests whether self-supervised learning helps when labelled data is scarce, and runs the model on a live sensor stream.

The project in one minute

A smartphone records how it moves: three accelerometer axes (acceleration, including gravity) and three gyroscope axes (rotation). Each activity leaves a different pattern in those six signals. We cut the stream into 3-second windows and train a neural network to name the activity.

Raw sensors→150-sample windows→Normalize→Self-supervised pretraining→Classifier→Activity + confidence

Research question: can learning from unlabelled sensor data improve recognition when only a few labelled windows exist?

Short answer so far: not at 5% to 100% labels, and possibly yes at 1% labels. The evidence at 1% is suggestive, not conclusive.

Key ideas in plain words

Window
A short slice of the sensor stream, 150 readings (about 3 seconds). The model classifies one window at a time.
Normalization
Rescaling each sensor channel so values are comparable. We compute the scaling from training data only, so the test data stays unseen.
1D CNN
A neural network that slides small filters along the time axis to spot patterns such as the rhythm of steps.
Self-supervised learning
Teaching the network from data without labels. We show it two slightly distorted copies of the same window and train it to recognise they match, so it learns what makes a window distinctive.
Label efficiency
How well a method works when only a few windows have activity labels. This is where self-supervised learning is supposed to help.
Domain shift
When data at test time looks different from training data, for example a phone held in the hand instead of worn at the waist. It is the main risk for our live demo.

The data

We use the UCI HAR dataset in the standardized DAGHAR format. Each sample is a window of 6 channels x 150 time steps. There are 2420 training, 340 validation and 690 test windows across 5 balanced classes.

  • Subject-independent split. 21 users train, 3 validate, 6 test, and no user appears in two splits (we checked). The test measures performance on people the model never saw.
  • Classes: sitting, standing, walking, upstairs, downstairs. The names are inferred from the original UCI numbering and the signal statistics, and need confirming against the DAGHAR documentation.
  • Not available: running. This dataset has no running class.
  • Units: accelerometer looks like g with gravity mostly on x, gyroscope like rad/s. The 50 Hz sampling rate is an assumption we still have to verify.

Honest reading. This task is easy enough that a plain CNN already reaches about 93% with 120 labelled windows, leaving little room for pretraining to help. SSL was ahead at 1% in all three seeds, but with three seeds and overlapping error bars we call that a hint. The encoder was pretrained once, and the validation set (340 windows) chose the best epoch even in low-label runs, which is slightly optimistic.

The live prototype

Phone (held in hand)→Wi-Fi→Flask server→Sliding buffer→Same preprocessing→Model→Dashboard

The server keeps recent samples, resamples them to the training rate, normalizes them exactly as in training, and predicts about every half second, smoothing over the last three predictions.

Proving the pipeline before using a phone

The replay test streams real test windows through the same server. Its accuracy should match the offline accuracy, and it does. It is a simulation (recorded data, not a phone) and is labelled as one. It skips the phone unit and axis conversion, which only the real phone can test. VerifiedReplay accuracy 0.9391 on all 690 test windows, identical to the offline 0.9391, with no missing predictions.

Why a hand-held phone changes things. The training phone was worn at the waist. A phone in the hand swings with the arm and is held at a varying angle, so we expect lower accuracy than offline, especially for sitting versus standing and for the stair classes. The axis and unit mapping must be calibrated on the real phone. For the demo the phone is held in one fixed pose. Other placements, and fine-tuning on a small set of our own hand-held recordings, are planned next.

Limits and next version

  • One dataset, five classes, waist-mounted recordings.
  • Sampling rate and class names still to confirm.
  • Limited SSL evidence: one pretraining run, three fine-tuning seeds.
  • Real-phone hand-held accuracy has not been measured yet.

Next version: other placements (pocket, bag, wrist-worn), a second dataset with running, more SSL methods and encoders, 10 or more seeds with statistical tests, and a small set of our own recordings for fine-tuning.
